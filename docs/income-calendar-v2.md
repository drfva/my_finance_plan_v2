# Автоматические доходы, распределение и календарь

## Доходы и ручные значения

У выплаты хранится признак `income_manual`. У незакреплённой выплаты с `calc_mode != 'manual'` и `income_manual = false` доход пересчитывается при изменениях отпусков, оклада и календаря. Распределение использует пересчитанный доход сразу, независимо от старого значения `income_net`.

Правка суммы в Доходах устанавливает `income_manual = true`: такая сумма сохраняется при пересчётах и получает выделенную рамку. Кнопка «Подставить по формуле» возвращает автоматический режим. Разовые ручные выплаты остаются ручными. Закрепление выплаты сохраняет рассчитанный доход и все отчисления, включая случай, когда часть отчислений была задана вручную.

У старых записей `income_manual = NULL`: приложение один раз сравнивает сохранённую сумму с формулой. Совпадение с точностью до 50 копеек включает автоматический режим; отличающаяся сумма сохраняется как ручная. История происхождения старых сумм неизвестна, поэтому отличающееся устаревшее автоматическое значение потребуется один раз вернуть к формуле кнопкой.

Рамка ручных значений также используется у отпускных, индивидуальных сумм расходов, отчислений по целям, платежей по картам, сумм подарков на конкретный год и правок строк, созданных шаблонами целей. У платежей рассрочек `manual_fields` отдельно хранит правку суммы и даты; пересборка будущего графика сохраняет эти поля, оставшуюся сумму делит между автоматическими платежами. Настройки рамкой не помечаются.

## Распределение по срокам

Расчёт сначала строит план, затем уточняет распределение с учётом будущих выплат. Проверяется потребность не только отдельной цели, но и всех целей вместе к каждой дате. Если будущих свободных выплат не хватит, необходимые деньги оставляются ближайшим срокам уже сейчас, даже если соответствующий раздел конвейера расположен позже. При этом учитываются обязательные расходы и платежи, закреплённые выплаты, ручные отчисления и заданный темп подушек.

Будущие ручные отчисления уменьшают сумму, которую нужно распределить автоматически. Ручная прибавка в одной выплате может уменьшить следующие автоматические отчисления, когда итоговый план по-прежнему покрывает потребность к сроку. Запланированная до срока трата учитывается заранее. При нескольких этапах проверяется потребность по последовательным этапам; штатная трата накопленного резерва не требует повторного накопления той же суммы.

Проверка сценария «Подарки / Лазерная эпиляция / Велосипед» использует указанные суммы, остатки, сроки и даты выплат, а свободные суммы выплат задаёт тест. Данные реального плана из базы при проверке не загружались. Изменения не гарантируют выполнимость плана при недостатке денег или ограничениях, заданных вручную.

## Календарь в Настройках

Вместо таблиц исключений отображается календарь месяца с переходом влево и вправо, включая смену года. Отдельно выделены рабочие дни, выходные и праздники; показано количество рабочих и нерабочих дней. Выбор дня позволяет назначить рабочий день или праздник, а «По календарю» удаляет личное исключение. Читатель плана может листать месяцы, но не менять дни.

Календарь использует справочник производственного календаря и исключения плана. Ручное количество рабочих дней месяца по-прежнему поддерживается: при его наличии рядом показано и рассчитанное по дням количество. Удаление ручного количества возвращает расчёт по календарю.

## Обновление базы

Перед обновлением приложения выполнить `v2/sql/008_income_manual.sql` в SQL Editor каждой используемой базы. Скрипт добавляет `periods.income_manual` и `installment_payments.manual_fields`, затем обновляет кеш схемы API. Его можно выполнять повторно. Для предыдущих изменений целей требуется ранее применённый `007_goal_archive.sql`.

Для чистой базы `v2/install.sql` включает обновления 001–008. На существующей базе нужен отдельный скрипт 008, а не полная установка. Приложение сохраняет новые признаки через существующие `state_save` / `state_get`.
