# Семейный план: реализация и запуск

Реализовано по `family-plan-spec.md` и ответам в чате от 31.10.2026. Само ТЗ сохранено без правок.

## Что доступно

- Отдельный семейный контекст: «Обзор», «Доходы», «Категории», «Расходы» (план/факт), «Настройки», «История изменений».
- Одна семья на пользователя, один личный источник в RUB. Создание семьи и принятие приглашения не включают взносы автоматически: своё правило участник сохраняет в личных настройках.
- Все участники — владельцы общего бюджета: меняют название, категории и любые общие расходы, приглашают и исключают участников. Каждый меняет только собственные никнейм, цвет, правило и будущие взносы. Проведённые взносы не редактируются.
- Приглашение по почте действует 7 дней, отзывается, поддерживает новых пользователей и повторное вступление. До принятия доступа к семье нет. Никнейм — до 40 символов, цвета могут совпадать.
- Взносы: сумма с выплаты, сумма за месяц, процент от полной выплаты на руки, свободный остаток. Поддержаны лимит суммой/процентом свободного остатка на выплату/месяц и общий потолок с одной выплаты.
- Семейный этап добавляется в конец личной очереди распределения. Его можно переместить выше других этапов; оставшиеся личные расходы, долги и накопления рассчитываются из оставшихся денег.
- В личных настройках блоки «План» и «Семейный план» раскрываются. Название текущего плана и роль показаны перед доступными планами, текущий план выделен рамкой. Форма отчислений показывает параметры выбранного способа: сумму, процент либо лимиты свободного остатка. Потолок с одной выплаты ограничивает весь взнос, включая добор; лимит свободного остатка действует на выплату или на месяц только в этом режиме.
- В раскрытой личной выплате отчисления показаны отдельным блоком после рассрочек и кредиток: сумма, правило и дата списания. В свёрнутой выплате отдельной семейной плашки нет. Настройка собственного никнейма и палитра цветов находятся прямо в «Участниках семьи», там же — приглашения со статусами и действие выхода. Изменения профиля сохраняются автоматически.
- Месячная сумма распределяется пропорционально доходам оставшихся выплат. Обязательный недобор погашается от самого раннего месяца с соблюдением потолка. Неиспользованный лимит свободного остатка долгом не становится.
- Смена месячной суммы заменяет общий план текущего месяца с зачётом уже переданного. Если план ниже переданного, возврата нет. Смена месячного режима на другой отменяет неоплаченный остаток текущего месяца; старый недобор сохраняется.
- При уменьшении базы месячного процентного лимита проведённые суммы сохраняются. Превышение видно в личной выплате, новые взносы прекращаются до освобождения лимита/следующего месяца.
- План расходов задаётся фиксированными суммами на выбранный месяц. Автоматического повторения и переноса остатка/дефицита бюджета нет. Статистический факт не меняет остаток и отчисления. Погашенный в следующем месяце недобор — доход следующего месяца с указанием периода возникновения.
- Прогноз отделён от полученных денег. Открытие страницы и обновление прогноза не проводят взносы. Серверная задача каждый час обрабатывает наступившие и пропущенные даты по Москве и одновременно фиксирует личную выплату и семейное поступление.

## Совместимость и данные

Планы без семейного подключения используют прежний расчёт. Категории семьи не связаны с личными. В семейный ответ API не попадают чужие доходы, доступный остаток, параметры правила и внутренний журнал расчёта. Ранее выданный обычный доступ к личному плану сохраняется: его читатель видит корректный баланс с вычетом семейного взноса, редактор может обновлять прогноз этого источника, но не менять чужое правило.

Один источник нельзя одновременно подключить двум участникам: это предотвращает двойное списание из одной выплаты. После первого проведённого взноса смена источника в рамках текущего участия закрыта. Повторное вступление создаёт новое участие без переноса старого правила и недобора.

Выход/исключение прекращает будущие отчисления и добор. Последний участник получает предупреждение об удалении плана. План удаляется из доступа всех пользователей; техническая запись с историей и проведёнными взносами сохраняется, чтобы не изменить прошлые личные балансы. Аудит не очищается автоматически.

Сохранения семейных команд последовательны и защищены версиями и идентификатором запроса. Повтор сетевого запроса не создаёт дубликат. Фиксация исходной выплаты и поступления выполняется одной транзакцией; конфликт изменений пересчитывается на свежих данных. При неизвестном налоге больничного выплата и последующие взносы остаются прогнозом до уточнения расчёта, чтобы сохранить порядок погашения недобора.

## Применение в Supabase

Сначала применить к тестовому проекту Supabase и проверить на тестовом адресе GitHub Pages. Эти действия в удалённых проектах агентом не выполнялись.

### 1. База данных

Для существующей базы с установленными `v2/sql/001…010` выполнить в SQL Editor **только**:

`supabase/migrations/20261031172114_family_plan.sql`

Она добавляет таблицы, защищённые RPC, аудит и этап распределения без сброса личных данных. Не выполнять `000_reset_public.sql`. Для полностью чистого проекта вместо отдельных файлов использовать обновлённый `v2/install.sql`: в него включены 001…010 и семейная миграция в общей транзакции.

После изменения исходных SQL установщик пересобирается командой:

```sh
node tools/build-install.mjs
```

### 2. Серверная функция

В корне репозитория подготовить общие расчётные модули для Edge Function:

```sh
node tools/build-family-function.mjs
```

Команда формирует игнорируемую Git папку `supabase/functions/_shared/finance/`. Она содержит те же модули, которые использует браузер; отдельных формул для сервера нет. Повторять перед каждым развёртыванием функции после изменения движка.

В Supabase → Edge Functions → Secrets установить:

| Имя | Значение |
| --- | --- |
| `FAMILY_APP_URL` | Полный адрес приложения с завершающим `/`, например `https://USER.github.io/REPO/` |
| `FAMILY_APP_ORIGIN` | Только origin этого адреса, например `https://USER.github.io` |
| `FAMILY_CRON_SECRET` | Случайный секрет длиной не менее 32 символов, отдельный для теста и прода |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` функция получает из встроенных серверных переменных Supabase. Ключ service role не добавлять в `config.js` и файлы сайта.

С авторизованным Supabase CLI из корня репозитория:

```sh
supabase functions deploy family-worker --project-ref PROJECT_REF --use-api
```

В `supabase/config.toml` для этой функции задано `verify_jwt = false`: функция сама проверяет пользовательский Bearer через Auth `/user`, а запрос расписания — отдельным секретом. Пользовательский запрос может только обновлять прогноз и доставлять приглашения; провести взнос подменой тела запроса нельзя.

### 3. Почта и переход по приглашению

В Authentication → URL Configuration добавить разрешённый адрес возврата приложения, включая семейный параметр ссылки. Для GitHub Pages подойдёт шаблон `https://USER.github.io/REPO/**`; тестовый и продовый адреса настроить в соответствующих проектах. `FAMILY_APP_URL` должен указывать на тот же адрес.

Настроить SMTP для реальной доставки. Шаблоны Invite user и Magic Link должны использовать стандартную `{{ .ConfirmationURL }}` и сохранять переданный redirect. Новый пользователь получает Auth invitation, зарегистрированный — Magic Link; после входа приложение предлагает явно принять семейное приглашение.

Очередь писем закрыта от браузерного API. Ошибка доставки сохраняется для повтора с задержкой; отправленное письмо не означает принятие приглашения. Отзыв закрывает доступ даже по уже доставленной ссылке.

Справка Supabase: [redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [шаблоны писем](https://supabase.com/docs/guides/auth/auth-email-templates).

### 4. Расписание

В Supabase Vault создать два секрета через интерфейс проекта:

- `finance_family_worker_url` — `https://PROJECT_REF.supabase.co/functions/v1/family-worker`.
- `finance_family_cron_secret` — точно то же значение, что `FAMILY_CRON_SECRET` функции.

Затем выполнить `tools/configure-family-cron.sql`. Скрипт подключает Cron/pg_net, проверяет секреты Vault и создаёт задание `finance-family-hourly` на начало каждого часа. Повторный запуск заменяет только это задание. Все источники отправляются пакетами по 10; очередь писем обрабатывается и без подключённых источников.

Час запуска Cron не определяет дату выплаты: её функция вычисляет по `Europe/Moscow`. После недоступности сервера следующий запуск обрабатывает пропущенные даты без повторных взносов. Проверять результаты можно в Cron Job Runs и логах Edge Function; финансовые ошибки обработки возвращаются как коды по участникам, без содержимого личного плана.

Справка: [запуск Edge Functions по расписанию](https://supabase.com/docs/guides/functions/schedule-functions).

### 5. Сайт и контрольный сценарий

Опубликовать обновлённые статические файлы обычным способом. `config.js` должен выбирать URL и публичный ключ именно той базы, в которой выполнены предыдущие шаги. Тест и прод настраиваются раздельно.

1. В личных настройках раскрыть «Семейный план», создать семью, открыть её, добавить категорию и месячный план.
2. Пригласить второй тестовый адрес, открыть письмо и принять приглашение. Проверить роль владельца и отсутствие автоматических взносов до сохранения своего правила.
3. В личном источнике раскрыть «Семейный план», выбрать способ и сохранить правило, проверить положение этапа «В семейный план». В семье будущая сумма должна появиться прогнозом, не полученными деньгами. В личной выплате блок со списанием должен находиться после долгов.
4. Изменить свой будущий взнос, вернуть «По правилу». У другого участника эта сумма недоступна для редактирования.
5. В закрытом приложении дождаться задания после даты тестовой выплаты. Проверить один проведённый взнос и зафиксированную личную выплату. Повторить запуск — сумма не удваивается.
6. Проверить план 80 000 ₽ и факт 75 000 ₽ при полученных 100 000 ₽: остаток 20 000 ₽. Следующий месяц не получает этот остаток.
7. Проверить выход тестового участника, сохранение поступления и остановку прогноза. Последний участник должен увидеть предупреждение об удалении.

Реальная доставка почты, среда Edge Runtime и Cron проверяются этим сценарием после настройки проекта; локальные тесты их не заменяют.

## Локальная проверка

```sh
node --test tests/*.test.mjs
node tools/build-install.mjs
node tools/build-family-function.mjs
node --test tests/family.database.mjs
```

Для последней команды нужен отдельно установленный `@electric-sql/pglite@0.5.14`. Можно указать абсолютный путь к его `dist/index.js` в переменной `FINANCE_PGLITE_MODULE`. Эти тесты используют PostgreSQL в памяти и не подключаются к Supabase. Проверяются реальные миграции и SQL, права, версии, повторы, атомарное проведение, приглашения/выход, чистый установщик и запросы расписания с локальными заглушками Cron/HTTP.

`tools/preview/family-server.mjs` поднимает изолированный предпросмотр с вымышленными данными на `127.0.0.1` и временной базой в памяти. Письма не отправляются: маршрут `/mailbox?user=c` имитирует тестовый почтовый ящик. Этот сервер не публиковать и не использовать как рабочее приложение.
